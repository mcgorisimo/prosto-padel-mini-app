# AGENTS.md — правила работы для Codex

## Проект
Приложение для падел-клуба «Просто Падел»: текущий канал — Telegram Mini App,
целевые каналы после стабилизации backend — iOS и Android.

Целевая инфраструктура — Selectel. Supabase является только legacy-контуром и
должен быть полностью удалён из runtime, тестового окружения и зависимостей.

Цель MVP:
игрок может зарегистрироваться, создать открытый матч, увидеть матч в ленте, присоединиться к матчу, занять слот, написать в чат, создать приватную бронь.

## Главный продуктовый сценарий MVP
1. Вход / регистрация.
2. Создание открытого матча.
3. Матч появляется в ленте.
4. Детали матча открываются.
5. Игрок присоединяется.
6. Слот сохраняется.
7. Чат работает.
8. Приватная бронь не попадает в публичную ленту.

## Строгие правила
- Не переписывать App.jsx целиком.
- Не менять дизайн без необходимости.
- Не добавлять новые обращения или зависимости Supabase.
- Не переносить новые функции в Supabase: данные, auth и бизнес-операции принадлежат backend/PostgreSQL в Selectel.
- Не добавлять новые функции без отдельной команды.
- Не трогать payment-поля: paymentStatus, ownerPaid, holdAmount, prepay.
- Работать маленькими изменениями.
- Не делать длинные отчеты.
- Не пересказывать весь проект.
- Если задача непонятна — сначала посмотреть код, не задавать лишние вопросы.
- Если найден баг — исправить минимально.

## Формат работы
1. Прочитать TASK.md.
2. Для задач недельного launch-спринта прочитать:
   - docs/launch/MASTER_PLAN.md
   - docs/launch/WORKLOG.md
3. Изменить только нужные файлы.
4. Запустить:
   npm.cmd run test:e2e
   npm.cmd run build
5. Если изменён backend, дополнительно запустить в backend:
   npm.cmd run typecheck
   npm.cmd run test:unit
   npm.cmd run test:e2e
   npm.cmd run build
6. Обновить docs/launch/WORKLOG.md только если результат соответствует политике
   WORKLOG ниже.
7. Проверить deployment impact и выполнить обязательный deployment gate ниже.
8. Дать короткий отчет:
   - файлы изменены
   - что исправлено
   - test:e2e результат
   - build результат
   - commit/push/merge результат
   - deployment status и deployed commit
   - health/smoke/log результат
   - что осталось

## Политика WORKLOG
- WORKLOG — журнал контрольных точек, а не протокол переписки или каждого шага.
- Добавлять одну короткую запись только при наличии хотя бы одного события:
  - создан или интегрирован commit/checkpoint;
  - выполнен deployment, migration, server/DB/provider write или rollback;
  - принято архитектурное либо продуктовое решение владельца, влияющее на
    следующие задачи;
  - обнаружен blocker, меняющий gate, порядок работ или безопасность;
  - завершён этап, для которого другому чату нужен воспроизводимый handoff.
- Не обновлять WORKLOG для read-only анализа, консультации, промежуточной
  проверки, обычного review без gate-changing findings или незавершённой работы.
- Одна запись — максимум 5–10 коротких строк: дата/этап, exact SHA при наличии,
  фактический результат, deployment status, blocker и следующий gate.
- Не помещать в WORKLOG полные отчёты, тексты заявок/документов, подробный ход
  рассуждений, команды, повтор истории, raw output, секреты или персональные данные.
  Подробный самостоятельный артефакт хранить в отдельном файле только когда он
  действительно нужен.
- Не создавать отдельный WORKLOG-only closeout commit без продуктового,
  эксплуатационного или утверждённого документационного результата.
- Итог задачи всегда сообщать владельцу прямо в чате. Нельзя заменять ответ
  ссылкой на WORKLOG или требовать от владельца читать его самостоятельно.

## Обязательный deployment gate
- Перед закрытием каждого этапа определить, меняет ли он runtime, container image,
  compose/config, зависимости, frontend bundle, backend или инфраструктуру.
- Если меняет — этап нельзя отмечать `done` и чат нельзя закрывать, пока целевой
  test-сервер не обновлён до точного commit и не пройдены health, бизнес-smoke и
  проверка логов.
- Сначала commit и интеграция в `main`, затем отдельный контролируемый test rollout.
- Если deployment явно отложен пользователем, записать `deployment_deferred_by_user`
  в итоговом ответе и, если этап требует handoff по политике выше, в WORKLOG;
  нельзя молча считать его выполненным.
- Production deployment выполнять только по отдельной прямой команде пользователя.
- Для docs-only/test-only изменений deployment может быть `not_needed`; это
  указывается в итоговом ответе и не требует отдельной записи WORKLOG.
- Финальный handoff всегда содержит: deployed environment, deployed commit,
  изменённые containers, health/HTTP, ручной smoke и результат проверки логов.

## Экономия лимита
- Не делать полный аудит проекта без запроса.
- Не читать все файлы подряд.
- Использовать точечный поиск rg.
- Не писать длинные объяснения.
- Не предлагать 10 следующих шагов.

## Работа в нескольких задачах Codex
- Один чат/задача отвечает за один ограниченный этап из MASTER_PLAN.md.
- Перед изменениями проверить ветку и git status; последнюю запись WORKLOG.md
  читать только если задача зависит от launch/deployment/migration handoff.
- Не вести параллельные изменения App.jsx, одной migration или одного доменного модуля в разных задачах.
- Субагенты допустимы для независимого исследования, тестов и review; итоговую интеграцию делает основной агент задачи.
- Завершённый этап оставляет handoff в WORKLOG.md только по политике выше.
- Новый чат обязан проверить последний deployment status; Git `done` не означает,
  что тот же commit уже работает на сервере.
